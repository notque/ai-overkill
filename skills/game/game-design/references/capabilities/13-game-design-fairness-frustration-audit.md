# game-design-fairness-frustration-audit

## Purpose

Separate productive challenge from preventable frustration. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: rules, RNG, queues, progression losses, support issues. Then inspect these capability-specific signals: agency, predictability, proportional cost, recovery, consistency, social trust. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Evaluate agency, predictability, consistency, proportionality, transparency, counterplay, recovery, and social legitimacy.
2. Compare actual rules, visible rules, and the rule the player reasonably inferred.
3. Separate productive tension from avoidable loss of trust.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- fairness scorecard
- frustration mechanism
- severity
- minimal fix
- trust guard

## Failure modes

- Do not invoke difficulty to excuse invalid information.
- Do not use frustration reports as proof that challenge is wrong.
- Do not excuse opaque punishment as hardcore design.

## Example application

When a team needs to separate productive challenge from preventable frustration, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `agency` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `social trust` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `fairness diagnosis and guardrails` with an owner, a quality guard, and a stop rule.

## Validation

Test the same scenario with players before and after the smallest clarity or counterplay change.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
