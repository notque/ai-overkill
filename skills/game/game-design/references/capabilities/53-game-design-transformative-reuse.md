# game-design-transformative-reuse

## Purpose

Borrow a familiar pattern only after changing its player purpose. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: references, genre norms, current design, player promise. Then inspect these capability-specific signals: source pattern, need, changed verb, new consequence, learning benefit, differentiation. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Describe the borrowed pattern, player need, changed verb, changed consequence, learning benefit, and differentiated promise.
2. Keep useful genre affordances while transforming the reason and result of the action.
3. Document references as inspiration, not as a mandate to reproduce expression or assets.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- reuse brief
- source-to-delta map
- differentiation test
- legal/creative boundary notes

## Failure modes

- Do not copy surface form and call it transformation.
- Do not reject all familiar patterns when they reduce learning cost.
- Do not confuse copying surface form with useful lineage.

## Example application

When a team needs to borrow a familiar pattern only after changing its player purpose, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `source pattern` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `differentiation` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `transformative reuse brief` with an owner, a quality guard, and a stop rule.

## Validation

Ask players what feels familiar and what feels meaningfully different.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
