# game-design-emotional-canvas

## Purpose

Specify intended feeling through playable cues. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: brief, UX flow, art and audio assets, player observations. Then inspect these capability-specific signals: target state, contrast, bodily tempo, sensory palette, interaction shape, rejection criteria. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Define target feeling, ingredients, contrasting feelings, sensory palette, interaction tempo, narrative tone, and no-go conditions.
2. Translate each feeling into a player action, feedback signal, visual/audio property, and rejection criterion.
3. Use contrast intentionally: tension needs relief; delight needs surprise without unreadability.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- emotional canvas
- cue-to-feeling map
- production implications
- rejection tests

## Failure modes

- Do not use an emotion word without playable evidence.
- Do not let art direction contradict required game readability.
- Mood words without interaction implications are incomplete.

## Example application

When a team needs to specify intended feeling through playable cues, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `target state` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `rejection criteria` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `emotional canvas` with an owner, a quality guard, and a stop rule.

## Validation

Run a short moment test and collect both observed behavior and player language.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
