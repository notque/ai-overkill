# game-design-player-values-mapper

## Purpose

Map values a game invites players to express or reject. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: choices, rewards, language, social rules, community evidence. Then inspect these capability-specific signals: care, mastery, fairness, creativity, belonging, competition, discovery, respect. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Map declared and enacted values through player choices, rewards, language, social rules, pricing, and moderation.
2. Test value tensions such as fairness versus status, care versus efficiency, and expression versus optimization.
3. Identify where the reward structure teaches the opposite of the stated value.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- value-to-system map
- contradiction register
- design corrections
- communication implications

## Failure modes

- Do not treat a value statement as implementation.
- Do not assume an intended value is perceived.
- Stated values fail if rewards teach the opposite.

## Example application

When a team needs to map values a game invites players to express or reject, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `care` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `respect` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `value-to-system map` with an owner, a quality guard, and a stop rule.

## Validation

Use scenario tests and community evidence to check what behavior the system actually honors.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
