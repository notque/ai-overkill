# game-design-one-page-design-doc

## Purpose

Compress a decision-ready feature or game brief into one page. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: design notes, build, roadmap, research. Then inspect these capability-specific signals: player promise, loop, pillars, audience, scope, risks, evidence, test, owner. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Force a single page to answer player promise, audience, loop, pillars, scope, evidence, risks, dependencies, test, and owner.
2. Use diagrams or tables only when they replace ambiguity.
3. Write unresolved assumptions visibly rather than hiding them in links.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- one-page brief
- decision summary
- assumptions
- acceptance test

## Failure modes

- Do not make the page a marketing summary.
- Do not shrink text to avoid a scope decision.
- One page is a forcing function, not an excuse to omit risk.

## Example application

When a team needs to compress a decision-ready feature or game brief into one page, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `player promise` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `owner` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `one-page decision document` with an owner, a quality guard, and a stop rule.

## Validation

A cross-discipline reader should be able to name the next build/test without a meeting.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
