# game-design-brainstorm-methods

## Purpose

Choose an ideation method that changes the decision. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: decision statement, constraints, existing options, evidence. Then inspect these capability-specific signals: constraint, assumption reversal, analogy, forced variation, role shift, removal. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Select the divergent method by blockage: How-Might-We reframes, SCAMPER transforms, Crazy 8s accelerates, six hats changes stance, brainwriting equalizes contribution, worst-idea removes inhibition, forced connections creates analogy, lotus expansion broadens, and morphological analysis recombines variables.
2. Set a fixed decision, constraints, timebox, and evaluation criteria before generating.
3. Converge only after options differ in player goal, information, pressure, consequence, social relation, or scope.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- method selection rationale
- prompt set
- raw option set
- clustered themes
- evaluated shortlist
- next experiment

## Failure modes

- Do not run ideation when the missing item is player evidence.
- Do not count renamed implementation variants as different options.
- Do not schedule ideation when the missing need is evidence.

## Example application

When a team needs to choose an ideation method that changes the decision, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `constraint` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `removal` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `divergent options followed by selection rule` with an owner, a quality guard, and a stop rule.

## Validation

Verify that the final options produce distinguishable player moments and a real cut option.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
