# game-design-craft-critique

## Purpose

Critique how a player learns, notices, predicts, and masters. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: video, build, control scheme, tutorial, challenge sequence. Then inspect these capability-specific signals: readability, pattern discovery, feedback timing, variation, mastery ceiling. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Trace the learning ladder: notice, form a prediction, act, receive legible feedback, revise a model, and demonstrate mastery.
2. Separate surface polish from pattern readability, challenge composition, and expressive decision space.
3. Critique a concrete sequence rather than the game’s genre or ambition.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- moment transcript
- learning-model diagnosis
- craft strengths
- frictions
- sequence-specific revisions

## Failure modes

- Do not use “fun” as a finding.
- Do not add variation before players can read the base pattern.
- Ground every verdict in a specific player moment, choice, and observed consequence.

## Example application

When a team needs to critique how a player learns, notices, predicts, and masters, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `readability` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `mastery ceiling` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `moment-level craft critique` with an owner, a quality guard, and a stop rule.

## Validation

Test whether players can explain a new pattern and adapt it on the next encounter.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
