# game-design-thinking-fast-and-slow-audit

## Purpose

Match decision time, cue clarity, and reversibility to stakes. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: UX, combat, economy, dialog, settings. Then inspect these capability-specific signals: time pressure, default, salience, calculation burden, confirmation, irreversible cost. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Classify decisions by time pressure, stakes, reversibility, information load, default effects, and confirmation opportunity.
2. Move high-cost choices toward deliberate review; keep fast action readable and recoverable.
3. Audit how UI salience and defaults shape behavior.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- decision-mode table
- fast-choice hazards
- slow-choice friction
- rule/UI changes

## Failure modes

- Do not exploit impulsive moments for hidden commitment.
- Do not slow down low-stakes play without a player benefit.
- Do not exploit fast choices for costly or hidden commitments.

## Example application

When a team needs to match decision time, cue clarity, and reversibility to stakes, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `time pressure` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `irreversible cost` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `decision-mode audit` with an owner, a quality guard, and a stop rule.

## Validation

Test recall, regret, error recovery, and informed choice after the decision.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
