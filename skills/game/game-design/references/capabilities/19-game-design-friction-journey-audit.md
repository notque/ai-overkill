# game-design-friction-journey-audit

## Purpose

Locate effort that does not buy understanding, agency, or value. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: screens, flows, logs, performance, playtest recordings. Then inspect these capability-specific signals: entry, setup, navigation, choice, wait, recovery, social coordination, exit. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Map arrival, setup, navigation, learning, decision, waiting, failure, social coordination, exit, and return.
2. Classify friction as useful challenge, required setup, accidental effort, technical delay, or trust cost.
3. Remove or shorten accidental effort while protecting meaningful tension.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- journey map
- friction register
- cost/benefit classification
- quick wins
- structural fixes

## Failure modes

- Do not remove all effort from a mastery game.
- Do not reduce a journey to UI screens when systems cause the friction.
- Some effort is desirable when it creates tension or mastery.

## Example application

When a team needs to locate effort that does not buy understanding, agency, or value, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `entry` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `exit` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `journey friction register` with an owner, a quality guard, and a stop rule.

## Validation

Time and observe the journey; confirm that comprehension and agency increase after removal.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
