# game-design-systematizing-empathizing-audit

## Purpose

Offer both rule-oriented and relationship-oriented ways into a system. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: tutorial, rules, UI, content, player observation. Then inspect these capability-specific signals: model clarity, pattern depth, narrative or social resonance, optionality, cognitive load. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Offer rule-oriented entry through models, predictability, and depth; offer relationship-oriented entry through characters, consequences, and care.
2. Audit whether either path is blocked by needless cognitive load or social pressure.
3. Provide optional bridges rather than assigning people to fixed cognitive types.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- dual-entry audit
- blocked-path table
- UI/content options
- accessibility notes

## Failure modes

- Do not diagnose players or make identity claims.
- Do not remove rule clarity to make a system more emotional.
- Cognitive preference models are not diagnoses.

## Example application

When a team needs to offer both rule-oriented and relationship-oriented ways into a system, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `model clarity` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `cognitive load` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `entry-path and accessibility review` with an owner, a quality guard, and a stop rule.

## Validation

Test whether players with different stated approaches can form a plan and find meaning.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
