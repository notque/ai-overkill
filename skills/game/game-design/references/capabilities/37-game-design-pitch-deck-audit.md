# game-design-pitch-deck-audit

## Purpose

Test whether a pitch proves its player promise and production logic. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: deck, build, roadmap, financial plan, competitor evidence. Then inspect these capability-specific signals: audience, promise, proof, differentiation, market context, scope, team, ask. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Audit player, promise, proof, market context, differentiation, product evidence, team, plan, risk, and ask.
2. Check claim-to-evidence ratio slide by slide.
3. Separate a concept teaser from a fundable production argument.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- deck scorecard
- missing proof
- narrative order
- revised ask
- next evidence asset

## Failure modes

- Do not let visual polish conceal an undefined audience or plan.
- Do not claim differentiation without comparison evidence.
- Visual polish cannot replace a clear ask or playable proof.

## Example application

When a team needs to test whether a pitch proves its player promise and production logic, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `audience` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `ask` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `pitch deck critique` with an owner, a quality guard, and a stop rule.

## Validation

Ask a cold audience to state the player promise, proof, risk, and requested decision.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
