# game-design-social-satisfaction-matrix

## Purpose

Map social systems to autonomy, competence, relatedness, and status. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: guilds, parties, chat, rewards, moderation. Then inspect these capability-specific signals: social action, need served, asymmetry, opt-out, abuse path, recognition, repair. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Map a social feature against autonomy, competence, relatedness, and status.
2. For each cell assess action, benefit, asymmetry, opt-out, abuse path, recognition, and repair.
3. Use the matrix to find systems that reward exclusion, dependence, or humiliation.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- social-need matrix
- risk cells
- inclusive alternatives
- moderation/operations requirements

## Failure modes

- Do not treat status as a universal good.
- Do not require social exposure to access core competence.
- Status systems must not require humiliation or dependency.

## Example application

When a team needs to map social systems to autonomy, competence, relatedness, and status, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `social action` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `repair` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `social satisfaction matrix` with an owner, a quality guard, and a stop rule.

## Validation

Test voluntary participation, contribution clarity, sentiment, and safety reports together.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
