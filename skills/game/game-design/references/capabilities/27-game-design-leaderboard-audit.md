# game-design-leaderboard-audit

## Purpose

Audit comparison systems for fairness, belonging, and abuse. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: rank rules, matchmaking, rewards, moderation, player reports. Then inspect these capability-specific signals: metric, cohort, season, visibility, rewards, anti-cheat, new-player route, toxicity. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Audit purpose, score validity, cohort, season, reset, visibility, rewards, ties, anti-cheat, newcomer path, and opt-out.
2. Model status effects: aspiration, hopelessness, humiliation, collusion, pay advantage, and sabotage.
3. Prefer friends, cohorts, divisions, personal bests, or seasons when global dominance adds little value.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- leaderboard risk register
- fairness findings
- alternative topology
- operations requirements

## Failure modes

- Do not assume a rank creates healthy competition.
- Do not reward behavior that harms teammates or integrity.
- Global rank is not the default form of motivation.

## Example application

When a team needs to audit comparison systems for fairness, belonging, and abuse, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `metric` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `toxicity` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `leaderboard risk report` with an owner, a quality guard, and a stop rule.

## Validation

Test whether newcomers find a meaningful comparison and whether participation remains voluntary.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
