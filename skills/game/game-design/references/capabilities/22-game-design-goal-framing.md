# game-design-goal-framing

## Purpose

Write goals players can understand and choose around. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: copy, objective UI, level and quest design. Then inspect these capability-specific signals: desired state, urgency, action set, obstacle, consequence, feedback. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Write each goal as desired state, reason now, available action, obstacle, consequence, and success feedback.
2. Check whether the player has enough information to choose a plan without spoiling intentional discovery.
3. Make the first useful action visible at the moment motivation appears.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- goal frame
- player-facing copy
- information boundary
- test task

## Failure modes

- Do not make essential objectives cryptic merely to create mystery.
- Do not give goals without a reason or consequence.
- Do not conceal essential goals to create artificial mystery.

## Example application

When a team needs to write goals players can understand and choose around, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `desired state` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `feedback` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `goal framing specification` with an owner, a quality guard, and a stop rule.

## Validation

Use a cold read: can a new player state the goal and next action?

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
