# game-design-grow-design

## Purpose

Use goal, reality, options, and commitment to move a decision forward. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: decision log, roadmap, research, prototypes. Then inspect these capability-specific signals: desired outcome, current evidence, constraints, alternatives, next owner, review date. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Facilitate goal, current reality, options, and committed way forward in that order.
2. Separate facts, interpretations, constraints, and authority before asking for options.
3. End with an owned commitment, check date, and evidence required to revisit.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- GROW record
- decision gap
- option table
- commitment contract

## Failure modes

- Do not use facilitation to avoid naming a decision owner.
- Do not call a wish a goal.
- Coaching structure cannot substitute for authority or resourcing.

## Example application

When a team needs to use goal, reality, options, and commitment to move a decision forward, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `desired outcome` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `review date` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `facilitated decision plan` with an owner, a quality guard, and a stop rule.

## Validation

The method passes when the next action and decision condition are unambiguous.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
