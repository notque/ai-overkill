# game-design-zeigarnik-effect-audit

## Purpose

Use unfinished goals as voluntary anticipation with transparent control. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: quest log, session end, notifications, economy. Then inspect these capability-specific signals: open thread, player ownership, timing, closure option, absence consequence, return cue. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Map open threads, ownership, timing, closure choice, return cue, and absence consequence.
2. Distinguish curiosity and voluntary anticipation from chores, hidden timers, and punishment for leaving.
3. Provide a safe close or transparent continuation point.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- open-loop map
- return-value diagnosis
- pressure risks
- closure alternatives

## Failure modes

- Do not use incompletion to manufacture anxiety.
- Do not make absence erase meaningful progress without clear consent.
- Do not turn unresolved work into punishment for leaving.

## Example application

When a team needs to use unfinished goals as voluntary anticipation with transparent control, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `open thread` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `return cue` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `return-motivation audit` with an owner, a quality guard, and a stop rule.

## Validation

Test whether players describe a desired return rather than obligation or fear.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
