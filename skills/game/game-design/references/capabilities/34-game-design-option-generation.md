# game-design-option-generation

## Purpose

Generate options across goals, information, pressure, consequence, and scope. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: problem statement, current approach, evidence. Then inspect these capability-specific signals: decision axis, constraints, user value, cost, risk, reversible test. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Generate alternatives by changing goal, verb, information, pressure, consequence, cadence, social relation, and scope.
2. Include preserve, transform, combine, postpone, and cut forms.
3. Evaluate on player outcome, evidence, cost, risk, and reversibility.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- option landscape
- decision axes
- comparison matrix
- recommended experiment

## Failure modes

- Do not generate options from implementation alone.
- Do not bury the do-nothing or cut alternative.
- Do not start from implementation variants only.

## Example application

When a team needs to generate options across goals, information, pressure, consequence, and scope, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `decision axis` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `reversible test` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `option set and selection criteria` with an owner, a quality guard, and a stop rule.

## Validation

Use a short player scenario to show how each option changes behavior.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
