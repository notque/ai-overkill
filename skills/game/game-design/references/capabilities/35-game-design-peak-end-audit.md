# game-design-peak-end-audit

## Purpose

Shape memorable highs and endings without manipulative pressure. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: session flow, reward timing, narrative, UI, economy. Then inspect these capability-specific signals: earned peak, contrast, closure, unresolved invitation, cooldown, session exit. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Map effort, uncertainty, emotional intensity, reward, cooldown, closure, and return invitation across a session.
2. Separate earned peaks from arbitrary reward spikes and closure from absence pressure.
3. Design endings that preserve agency: close, choose the next intention, or leave safely.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- session emotion timeline
- peak candidates
- end-state audit
- changes and guards

## Failure modes

- Do not use unresolved loss or expiring reward as a substitute for a satisfying end.
- Do not stack peaks until none is memorable.
- Do not use loss threats to convert a close into a return loop.

## Example application

When a team needs to shape memorable highs and endings without manipulative pressure, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `earned peak` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `session exit` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `peak-end map` with an owner, a quality guard, and a stop rule.

## Validation

Ask players for the most memorable and final moment after a delayed recall.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
