# game-design-failure-loop-audit

## Purpose

Trace a loss from expectation through retry and learning. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: failure states, telemetry, replay, UI, playtest notes. Then inspect these capability-specific signals: expectation, information, attempt, result, feedback, cost, restart, lesson. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Trace expectation, preparation, attempt, result, explanation, loss cost, restart friction, adaptation, and retry.
2. Classify failure as skill, knowledge, execution, resource, luck, social coordination, or system error.
3. Preserve a useful lesson or a fair recovery proportional to the cost.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- failure-loop map
- failure taxonomy
- player quote hypothesis
- repair ladder
- retry test

## Failure modes

- Do not assume punishment teaches.
- Do not fix a hidden cause with a more verbose death screen alone.
- Failure is not useful merely because it is difficult.

## Example application

When a team needs to trace a loss from expectation through retry and learning, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `expectation` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `lesson` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `failure-loop audit and repair plan` with an owner, a quality guard, and a stop rule.

## Validation

Measure whether the next attempt changes appropriately and whether players can explain why.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
