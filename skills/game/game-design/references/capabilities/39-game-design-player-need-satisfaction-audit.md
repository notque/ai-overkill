# game-design-player-need-satisfaction-audit

## Purpose

Test autonomy, competence, and relatedness in concrete moments. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: feature flow, feedback, social systems, research. Then inspect these capability-specific signals: choice ownership, mastery feedback, belonging, exclusion, dependency, pressure. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Audit autonomy (meaningful ownership), competence (legible growth), and relatedness (valued connection) in a specific moment.
2. Map each need to affordance, feedback, threat, and repair.
3. Keep support voluntary; avoid dependency, forced groups, and false choice.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- need satisfaction matrix
- deprivation risks
- feature changes
- welfare guards

## Failure modes

- Do not use need satisfaction language to rationalize compulsion.
- Do not call cosmetic variation autonomy when consequences never differ.
- Need language must not justify engineered dependency.

## Example application

When a team needs to test autonomy, competence, and relatedness in concrete moments, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `choice ownership` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `pressure` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `need-satisfaction audit` with an owner, a quality guard, and a stop rule.

## Validation

Use observation and short reflection to test ownership, learning, and belonging.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
