# game-design-prosocial-session-chapters

## Purpose

Structure a session around contribution, recognition, and shared resolution. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: session flow, co-op rules, matchmaking, rewards, moderation. Then inspect these capability-specific signals: welcome, role clarity, mutual need, contribution, recovery, recognition, close. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Structure sessions as welcome, role clarity, mutual need, contribution, setback/recovery, recognition, and close.
2. Give each participant a legible contribution and a low-risk way to help.
3. Plan for unequal skill, quiet participation, drop-out, and rejoin.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- session chapter map
- contribution matrix
- social repair rules
- recognition plan

## Failure modes

- Do not force voice, friendship, or constant cooperation.
- Do not make weak players feel like liabilities.
- Do not force social exposure when solo play is a valid need.

## Example application

When a team needs to structure a session around contribution, recognition, and shared resolution, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `welcome` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `close` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `prosocial chapter map` with an owner, a quality guard, and a stop rule.

## Validation

Observe whether each player can name their contribution and a positive social moment.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
