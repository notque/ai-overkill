# game-design-novelty-spectrum-audit

## Purpose

Place novelty where players can learn it and value it. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: genre references, first session, gameplay systems, player research. Then inspect these capability-specific signals: familiar mental model, changed rule, novelty load, onboarding cost, payoff, differentiation. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Place each element on familiar-to-new mental-model layers: control, goal, rule, feedback, content, social norm, and business model.
2. Budget novelty so players learn one changed assumption at a time.
3. Use familiar anchors where novelty does not create differentiated value.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- novelty map
- learning-cost estimate
- anchor plan
- differentiation case

## Failure modes

- Do not market novelty that the player cannot recognize.
- Do not treat borrowed convention as creative failure.
- Difference alone is not a reason to add complexity.

## Example application

When a team needs to place novelty where players can learn it and value it, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `familiar mental model` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `differentiation` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `novelty placement plan` with an owner, a quality guard, and a stop rule.

## Validation

Test whether players can transfer a familiar model and identify the intentional difference.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
