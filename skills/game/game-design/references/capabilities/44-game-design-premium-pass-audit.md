# game-design-premium-pass-audit

## Purpose

Audit paid progression for clarity, choice, and non-punitive participation. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: store, rewards, quests, economy, support, legal constraints. Then inspect these capability-specific signals: paid value, free path, time demand, catch-up, expiry, disclosure, decline outcome. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Audit paid value, free path, time demand, reward cadence, catch-up, expiry, pricing disclosure, decline experience, and spending pressure.
2. Model first purchase, late entry, missed week, non-payer, and returning player paths.
3. Require an informed, non-punitive choice and a quality guard beside conversion.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- pass journey map
- value table
- pressure risks
- free/paid parity issues
- fixes
- welfare metrics

## Failure modes

- Do not use fear of loss or confusion as the core value proposition.
- Do not call a free track meaningful if its path is intentionally degraded.
- Do not hide cost or use fear of loss to replace value.

## Example application

When a team needs to audit paid progression for clarity, choice, and non-punitive participation, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `paid value` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `decline outcome` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `premium-pass review` with an owner, a quality guard, and a stop rule.

## Validation

Test comprehension of price, duration, rewards, catch-up, and declining before release.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
