# game-design-five-options

## Purpose

Generate genuinely different paths before choosing. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: problem framing, current proposal, limits. Then inspect these capability-specific signals: goal, fixed constraints, changed axis, cut option, reversal, risk. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Produce five paths by varying goal, verb, information, pressure, consequence, social relation, or scope.
2. Reserve one option for removal and one for a reversible test.
3. Evaluate each against the same player outcome and constraints.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- five distinct concepts
- comparison matrix
- elimination reasons
- recommended test

## Failure modes

- Do not present five UI skins of one mechanic.
- Do not choose before the options have a shared decision rule.
- Renamed implementations of the same idea do not count.

## Example application

When a team needs to generate genuinely different paths before choosing, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `goal` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `risk` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `five-option comparison` with an owner, a quality guard, and a stop rule.

## Validation

A reviewer must be able to state the different player behavior each option creates.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
