# game-design-fantasy-extractor

## Purpose

State the player fantasy as actionable identity and consequence. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: pitch, opening, repeated actions, art direction, copy. Then inspect these capability-specific signals: player verb, role, stakes, recurring proof, emotional payoff, contradiction. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Express fantasy as “I am / I do / it matters because,” grounded in recurring player verbs and consequences.
2. Trace proof moments in onboarding, core loop, rewards, social status, and climax.
3. Identify fantasy leaks where UI, grind, or unrelated systems make the player feel like a clerk instead.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- fantasy statement
- proof-moment map
- contradiction list
- alignment actions

## Failure modes

- Do not confuse setting, lore, or aesthetic with enacted fantasy.
- Do not state a fantasy that the first hour never proves.
- Theme words are not a fantasy without player action.

## Example application

When a team needs to state the player fantasy as actionable identity and consequence, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `player verb` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `contradiction` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `fantasy statement and evidence map` with an owner, a quality guard, and a stop rule.

## Validation

Ask players to describe who they are in the game after a representative session.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
