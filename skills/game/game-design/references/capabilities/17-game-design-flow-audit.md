# game-design-flow-audit

## Purpose

Audit challenge, skill, focus, feedback, interruption, and recovery. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: level sequence, sessions, UX, player behavior. Then inspect these capability-specific signals: challenge ramp, clarity, decision load, feedback speed, distraction, re-entry. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Plot player skill against challenge over time, then annotate clarity, focus, feedback speed, interruption, and recovery.
2. Identify anxiety spikes, boredom flats, overload clusters, and mastery plateaus.
3. Introduce one new demand at a time and provide a safe application before stacking complexity.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- flow timeline
- interruption map
- demand sequence
- pacing interventions

## Failure modes

- Do not equate flow with continuous reward or zero friction.
- Do not diagnose flow without a time sequence.
- Flow is not maximum intensity or uninterrupted reward.

## Example application

When a team needs to audit challenge, skill, focus, feedback, interruption, and recovery, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `challenge ramp` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `re-entry` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `flow map and pacing fixes` with an owner, a quality guard, and a stop rule.

## Validation

Observe attention, errors, voluntary persistence, and post-session recall across the revised segment.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
