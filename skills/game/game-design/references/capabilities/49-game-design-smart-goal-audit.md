# game-design-smart-goal-audit

## Purpose

Make design goals observable and decision useful. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: roadmap, backlog, research, acceptance criteria. Then inspect these capability-specific signals: specific outcome, measure, feasibility, promise relevance, date, owner, review condition. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Check specificity, observable measure, feasibility, player/pillar relevance, deadline, owner, and review rule.
2. Separate outcome, output, and activity measures.
3. Add a quality guard whenever the main number could be gamed.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- goal audit table
- rewritten goal
- assumptions
- check-in cadence
- stop condition

## Failure modes

- Do not treat a date and metric as sufficient meaning.
- Do not set a target without a baseline or decision consequence.
- Numeric targets without player meaning are incomplete.

## Example application

When a team needs to make design goals observable and decision useful, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `specific outcome` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `review condition` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `goal-quality audit` with an owner, a quality guard, and a stop rule.

## Validation

Review whether the team can tell, at the date, whether to continue, change, or stop.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
