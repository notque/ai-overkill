# game-design-molyneux-lens

## Purpose

Challenge a feature against the game’s promised experience. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: pitch, build, screenshots, player language. Then inspect these capability-specific signals: promise, player expectation, actual action, feedback, consequence, contradiction. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Compare promised fantasy, player expectation, repeated action, feedback, and consequence.
2. Locate the first moment where the game proves or breaks its implied role.
3. Recommend changes that align verbs and stakes, not merely marketing language.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- promise-to-play chain
- contradiction diagnosis
- repair options
- proof-moment test

## Failure modes

- Do not protect a premise that the play does not support.
- Do not judge the game only from the pitch.
- A clever premise does not excuse play that proves a different fantasy.

## Example application

When a team needs to challenge a feature against the game’s promised experience, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `promise` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `contradiction` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `promise-to-play critique` with an owner, a quality guard, and a stop rule.

## Validation

Ask new players what they expected and what they actually felt they were doing.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
