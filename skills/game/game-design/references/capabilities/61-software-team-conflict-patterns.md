# software-team-conflict-patterns

## Purpose

Retain the decision-quality method relevant to design collaboration. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: decision records, meeting notes, delivery risks. Then inspect these capability-specific signals: decision owner, evidence, disagreement type, escalation path, repair, documentation. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. For design collaboration, describe recurring observable behavior, decision impact, role/power context, prior attempts, and retaliation risk.
2. Classify the project mechanism—control, avoidance, indecision, chaos, blame, status, or weak communication—without clinical labels.
3. Choose boundaries, written decisions, reframing, narrowed authority, mediation, or escalation proportionate to safety and power.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- situation summary
- evidence versus interpretation
- project risks
- response strategy
- documented next move
- escalation conditions

## Failure modes

- Do not diagnose people or prescribe manipulation.
- Do not advise confrontation that increases retaliation risk.
- Do not import personnel diagnosis or therapeutic claims into game design.

## Example application

When a team needs to retain the decision-quality method relevant to design collaboration, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `decision owner` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `documentation` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `collaboration decision protocol` with an owner, a quality guard, and a stop rule.

## Validation

Evaluate whether the next move improves decision clarity, safety, and delivery rather than winning an argument.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
