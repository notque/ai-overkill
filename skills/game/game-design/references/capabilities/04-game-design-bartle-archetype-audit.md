# game-design-bartle-archetype-audit

## Purpose

Use play-style motives as feature hypotheses. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: observed choices, session contexts, feature use, segment research. Then inspect these capability-specific signals: achievement, exploration, expression, competition, social contact, avoidance. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Use achiever, explorer, socializer, and competitor motives as competing feature hypotheses, not personality labels.
2. Map each feature to actions, rewards, optionality, interference, and abandonment risk for each motive.
3. Use mixed-motive cases to expose conflicts such as optimization versus discovery.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- motive-fit matrix
- primary and secondary hypotheses
- anti-fit
- design trade-offs
- observation plan

## Failure modes

- Do not segment individuals permanently by an archetype.
- Do not reward one motive by invalidating another without an explicit product choice.
- Archetypes are prompts, never permanent player labels.

## Example application

When a team needs to use play-style motives as feature hypotheses, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `achievement` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `avoidance` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `motive-fit hypotheses and anti-persona` with an owner, a quality guard, and a stop rule.

## Validation

Observe whether players choose the offered action when a motive-consistent alternative is available.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
