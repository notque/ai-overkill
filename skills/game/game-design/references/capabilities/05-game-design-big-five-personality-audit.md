# game-design-big-five-personality-audit

## Purpose

Test whether a design tolerates varied comfort and novelty needs. This packet is a repository-aware operating procedure, not a label to apply to a design.

## Evidence intake

Inspect repository evidence before requesting context: optional paths, defaults, accessibility choices, playtest variation. Then inspect these capability-specific signals: novelty appetite, social exposure, challenge tolerance, order preference, emotional load. Ask only for external evidence, confidential player research, decision authority, or constraints unavailable in the repository.

Mark every claim as `observed`, `documented`, `measured`, or `inferred`. Give each inference a confidence level and a disproof route.

## Method

1. Treat openness, conscientiousness, extraversion, agreeableness, and emotional sensitivity as variation in comfort, not predictive identity.
2. Audit novelty load, structure, social exposure, competitive stress, and recovery options.
3. Design flexible entrances and exits instead of tailoring a feature to a presumed trait.

## Diagnostic questions

- What exact player moment or delivery decision is under review?
- Which capability lens above has the strongest evidence and which is only an inference?
- Which competing explanation would produce the same visible symptom?
- What is the smallest change or test that would separate them?

## Output schema

Return all of the following, not a generic summary:

- comfort-range matrix
- inclusion gaps
- default/optional path recommendation
- confidence notes

## Failure modes

- Do not infer psychological traits from demographic data or event logs.
- Do not medicalize normal differences in play preference.
- Do not infer traits from telemetry or market stereotypes.

## Example application

When a team needs to test whether a design tolerates varied comfort and novelty needs, begin with the available build path and the capability matrix above. Apply the named method to the affected moment, not an abstract feature description. If direct player evidence is absent, publish an evidence gap rather than a false conclusion; label the result as inferred and use the validation below to move it toward measured evidence.

## Decision procedure

1. Use `novelty appetite` as the first discriminating lens, because it is closest to the stated capability.
2. Compare it against `emotional load` before selecting a fix; this prevents a single-dimension conclusion.
3. Convert the result into `inclusion and choice-flexibility review` with an owner, a quality guard, and a stop rule.

## Validation

Test comprehension, comfort, and opt-out use across varied play contexts.

## Full-diagnostic disposition

In a complete repository diagnostic, run this packet and record `assessed`, `evidence gap`, or `not applicable` with a game-specific reason. A missing artifact is a finding; it never permits silent omission.
